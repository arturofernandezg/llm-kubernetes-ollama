## Decisiones tomadas y WHYs

### 1. Constantes de módulo (no settings)

**Elegida:** `_SET_RESOURCES_EXCEPTION_MIN_CONFIDENCE = 0.9` y `_SET_RESOURCES_EXCEPTION_MAX_RISK = "medium"` como constantes de módulo UPPER_SNAKE.
**Descartada:** nuevas entradas en `Settings` (env vars).
**WHY:** Los umbrales de la excepción son una autorización explícita del tutor con valores específicos, no parámetros de operación. Si fueran env vars, un operador podría reducir el umbral de confianza (ej. 0.5) via un ConfigMap y anular la garantía de seguridad. Las constantes de módulo son auditables en code review y no override-ables en producción sin cambiar el código.

### 2. `continue` en lugar de `return` en el loop 4.5

**WHY:** Si el diagnóstico genera dos comandos —un `set resources` autorizado y un `scale` posterior— el `return RemediationAction.ESCALATE` dentro del `if restarts` solo llegaría al primero. Con `continue`, el loop evalúa TODOS los comandos. El `scale` sigue siendo bloqueado por el siguiente iteration. Un test específico (`test_set_resources_plus_scale_escalates`) verifica este comportamiento.

### 3. Defensa en profundidad: excepción 4.5 ≠ auto-remediar

**WHY:** Incluso con la excepción activa y `DRY_RUN=false`, rule 4.6 (new > 2× current → escalate) y rule 5 (risk > max_risk → escalate) siguen activos. En la práctica, qwen2.5:1.5b suele devolver `risk=high` para OOMKilled — así que el E2E en cluster seguirá mostrando `escalate`, no `auto_remediate`. Esto es correcto y seguro. Para ver `auto_remediate` real se necesita que el LLM emita `risk≤low`, `confidence≥0.9`, bump de memoria ≤2×. El gate de seguridad es multicapa por diseño.

### 4. Bug de línea en docs (corregido en implementación)

El roadmap §TODO #2 y la sesión S6 decían "flip en línea 81". En `k8s/deployment-agent.yaml` la línea 81 es el valor de `REMEDIATION_ROLLBACK_ENABLED`, no de `REMEDIATION_DRY_RUN`. Este error entró cuando S5 añadió las tres env vars de rollback (`ROLLBACK_ENABLED`, `ROLLBACK_TIMEOUT`, `ROLLBACK_GRACE`) desplazando el fichero. La implementación usó la búsqueda por nombre de env var, no por número de línea. El flip correcto es línea 79.
