## Hecho
- **`/ship` — pre-vuelo destapó una feature sin commitear**: el working tree traía un **audit
  trail** en `agent/main.py` (+2 tests) que NO estaba en `588e3a9` (log estructurado de
  accountability en approve/reject humano: quién, qué variante, qué workload). Commiteada como
  `feat(audit)` → **`7e40837`**. Build Cloud Build SUCCESS + deploy + `smoke.sh` PASSED.
- **Arco chaos #1 sobre `7e40837`**: el **C-08 doble botón RENDERIZÓ perfecto** (Opción A ×2
  motor 64Mi ✅ / Opción B modelo 512Mi ⚠️ / Rechazar) — captura guardada
  `demo/mattermost_c08_double_button.png`. **Pero los botones Aprobar no funcionaban** (Rechazar
  sí).
- **Debug del bug** (evidencia, no adivinar): log del agente → **0 POSTs** de approve (solo el
  reject llegó). Log de **Mattermost** → la pistola humeante:
  `path:/api/v4/posts/{id}/actions/approve_engine, code:404, "not found handler triggered"`.
- **Causa raíz**: `_button` ponía `id = action`, y las acciones C-08 `approve_engine`/
  `approve_model` llevan **guion bajo**. La ruta de acciones de MM valida `action_id` como
  **alfanumérico** → el `_` da 404 y el click muere en Mattermost, nunca llega al agente.
  `reject`/`approve` (una palabra) sí matchean → por eso el reject y el approve legacy de 1 botón
  siempre funcionaron. El bug nació con el doble botón.
- **Fix** (`agent/mattermost.py`): nuevo `sanitize_action_id()` que reduce el `id` a `[A-Za-z0-9]`
  (`approve_engine`→`approveengine`); `context.action` conserva el `_` intacto (es lo que el
  handler lee y lo que firma el HMAC). No toca handler ni HMAC. **Test de regresión**
  (`test_mattermost.py`): `test_c08_variant_button_ids_are_alphanumeric` (ejercita el render REAL
  de `send_escalation_with_buttons` con `approve_variants`) + `test_sanitize_action_id_*`.
  Commit `fix(c08)` → **`2ac3c5d`**. Rebuild + deploy + rollout verde.
- **Arco chaos #2 sobre `2ac3c5d`**: aprobado **`approve_engine`** (64Mi) → posteó y parcheó OK
  (`AUDIT human decision: remediation approved, action=approve_engine`). **Fix validado E2E.** A
  +300s el health-check vio el pod aún OOM (stress=100M > 64Mi) → **`rolled_back`** + revert a
  32Mi. Teardown por `trap` limpio.
- **Métricas del run** (pod `agent-75975b75b7-fx5sf`): `remediation_total{human_approved}=1`,
  `feedback_verdict_total{rolled_back}=1`, `feedback_verdict_total{resolved_observed}=1`,
  `remediation_rollback_total{reverted}=1`, y **`aiops_incident_resolution_seconds{OOMKilled}`

- Capturas guardadas en `demo/`: `mattermost_c08_double_button.png` (render doble botón),

## Encontrado / gotchas
- **Bug C-08 underscore→404** (el gordo del día). El hueco que lo dejó pasar: los tests C-08
  existentes (`TestCommandVariantEscalation/Callback`) **mockeaban `send_escalation_with_buttons`**
  y solo verificaban `context.action` — nadie ejercitaba el render real ni el `id`. Cerrado.
- **Munición de ensayo (lección meta)**: el bug se cazó desde logs de dos componentes (agente:
  ausencia de POST; Mattermost: el 404 exacto), no adivinando. "Review the server log, not the
  button."
- **El smoke test deja rastro en Redis**: su webhook OOM sintético (`smoke-test-pod`,
  `arturo-chaos`) siembra `aiops:cooldown:*` + `incident:active:*` e **incluso intenta remediar**
  (kubectl set resources → NotFound, el deployment no existe). ⇒ limpiar Redis antes de un arco
  es **obligatorio** (contradice el "smoke solo encola" que dije al principio: encola *y* deja
  estado).
- **Ollama container sin `curl`** → warm falla (`curl: not found`, exit 127). Alternativas: warm
  desde el Mac vía `port-forward svc/ollama-svc 11434`, o saltarlo (el budget del arco 2100s
  absorbe el arranque en frío ~3min).
- **`chaos-oom.yaml` stress = 100M fijos** (`--vm-bytes 100M --vm-hang 0`, alloc infinito). ⇒ el
  ×2 del motor (64Mi) **SIEMPRE** dará `rolled_back`; solo el valor del modelo (512Mi) o ≥~128Mi
  **cura**. El botón que elige el operador determina cured vs rolled_back. El manifiesto lo
  documenta: "healthy fix = 0 restarts = cured; failing fix = OOM = revert".
- **Dos veredictos coexistiendo** (`rolled_back` + `resolved_observed`) confirmado en logs como
  **incidentes/fingerprints DISTINTOS** del re-fire del arco: el aprobado
  (`incident-...-1783957054`, pod `74dbcff6b5`) → rolled_back (fuerte, dueño); otro escalado-no-
  aprobado (`...-1783957295`, pod `6f465bdb66-ps85f`) resuelto solo → resolved_observed (débil).
  La jerarquía "la débil nunca pisa la fuerte" es **por fingerprint** y se respetó. Los 92.47s de
  R5 son del segundo incidente.
- **`kubectl set image` vs bump del manifiesto**: Jay commiteó el bump del YAML pero se saltó el
  `set image` — el cluster seguía en la imagen vieja hasta aplicar `set image` explícito. El
  commit del manifiesto no despliega por sí solo.
- Recordatorio Mac: `sed -i ''` (BSD) para el bump del tag.

## Decisiones + por qué
- **Commitear el audit trail (opción A) en vez de stashearlo**: código ya escrito y testeado,
  cierra la QA hostil "cualquiera del canal puede pulsar ×16" (ahora toda decisión queda atribuida
  y logueada), aditivo y grounding-consistente → superset de `588e3a9`, sin romper R5/F-17/C-07/
  C-08. Alternativa (stash + ship puro) descartada: perdía munición de ensayo por nada.
- **Fix = sanear el `id`, NO tocar las action strings ni el handler ni el HMAC**: el `id` es solo
  la clave de routing interna de Mattermost; `context.action` es la fuente de verdad que el
  handler lee y el HMAC cubre. Cambio mínimo, cero superficie nueva. Alternativa (omitir `id` y que
  MM lo genere) descartada por menos determinista/testeable.
- **No perseguir un `cured` fresco en `2ac3c5d`**: repetir el arco eligiendo el botón modelo
  (512Mi) daría cured pero **no prueba nada nuevo del fix** (approve_engine ya validado), y el
  replay `mattermost_cured.png` del 06-jul ya cubre el cured en el deck. Coste/beneficio: no.
- **`rolled_back` se queda como captura honesta**: el safety-net auto-revirtió un fix aprobado por
  un humano que resultó insuficiente — "safety ≠ correctness" en acción, munición fuerte.
- **Encuadre**: este proyecto es **prácticas/chapter, NO el TFG de Jay** (su TFG es otro). Sin
  peso académico; el chapter del 15-jul es opcional/de empresa.
