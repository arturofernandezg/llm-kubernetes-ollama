§0Veredicto ejecutivo

Sólido como prototipo de investigación y demo de chapter, con guardrails de seguridad genuinamente buenos. Pero no está listo para producción y tiene una desalineación arquitectónica con su propio objetivo declarado.

El punto 3 del flujo objetivo —"obtener información del incidente mediante la API de Kubernetes"— no se cumple: el LLM diagnostica prácticamente a ciegas. Esa única decisión arrastra la nota de IA, la de seguridad (confianza no calibrada gateando acciones) y es la causa raíz real de la alucinación de current_value que ya tenéis identificada como "slice C".

P0·1El hallazgo crítico: diagnóstico a ciegas

🔴 Bloqueante P0 El agente no enriquece el contexto con la API de Kubernetes antes de llamar al LLM. Todo lo demás es secundario a esto.

generate_diagnosis() (diagnosis.py:103) recibe únicamente alert.labels + alert.annotations (lo que manda Alertmanager) y el contexto RAG. Un grep confirma que no hay ni una sola llamada a kubectl logs / describe / get events en el camino de diagnóstico. El único uso de kubectl es posterior a la decisión (capture_pre_patch_value, check_pod_health).

La ironía: el agente tiene el RBAC para pods, pods/log y events (rbac.yaml:10-18)… y no lo usa para diagnosticar.

Consecuencias en cascada

  1. El modelo de 1.5B tiene que inventar current_value porque no está en las labels. La causa raíz no es el modelo pequeño: es que la fuente de verdad es el LLM en vez del cluster. Esto es exactamente vuestra "slice C" pendiente.
  2. La confianza que gatea la auto-remediación (remediation_auto_confidence=0.8) es autoevaluada por un 1.5B sobre contexto pobre → métrica no calibrada gateando una acción destructiva.

Solución concreta

Insertar una etapa determinista de context gathering entre la cola y el LLM:

# agent/enrichment.py (nuevo)
async def gather_incident_context(alert: AlertItem) -> IncidentSnapshot:
    ns, pod = alert.labels["namespace"], alert.labels["pod"]
    # todo en paralelo, timeout corto, fail-soft por campo
    logs, events, pod_json = await asyncio.gather(
        kubectl_json("logs", pod, "-n", ns, "--tail=50", "--previous"),
        kubectl_json("get", "events", "-n", ns,
                     "--field-selector", f"involvedObject.name={pod}"),
        kubectl_json("get", "pod", pod, "-n", ns, "-o", "json"),
        return_exceptions=True,
    )
    return IncidentSnapshot(
        restart_count=..., phase=..., last_state_reason=...,   # de pod_json
        current_limits=pod_json[...resources.limits],          # ← current_value REAL
        recent_events=events, log_tail=logs,
    )
current_value y el target salen de este snapshot, nunca del LLM. El LLM queda relegado a lo que hace bien (explicar y clasificar), no a producir hechos numéricos.

Por qué es mejor: convierte el sistema de "LLM que adivina el estado del cluster" a "LLM que razona sobre el estado real del cluster". Es la diferencia entre un juguete y una herramienta de SRE — y sella de un tiro la clase entera de alucinaciones que os bloquea.

P0·2Auth de callbacks fail-open + Secrets rotos

🔴 Bloqueante P0 Con REMEDIATION_DRY_RUN=false, cualquiera con acceso de red al pod puede aprobar y ejecutar remediaciones reales si el Secret no está.

_verify_hmac_token (main.py:150) devuelve True si webhook_secret está vacío. Igual el mm_command_token. Es fail-open: falta de secreto = sin autenticación.

Y encima el Secret probablemente no está

Hay un mismatch que desactiva HMAC en la práctica:

  • secrets-setup.sh:23 crea agent-secrets con clave mattermost-webhook-url.
  • El deployment lee el Secret mattermost-webhook clave url (deployment-agent.yaml:94) — otro nombre.
  • Y espera webhook-secret + mm-command-token en agent-secrets (:98-108), que el script nunca crea.

Resultado real: HMAC y token de slash-command deshabilitados → combinado con el fail-open, superficie de ejecución no autenticada.

Fix (1) Fail-closed cuando REMEDIATION_DRY_RUN=false: sin secreto → 401, no ejecutar. (2) Alinear secrets-setup.sh con las claves exactas que lee el deployment. (3) Marcar en docs como bloqueante de despliegue.

P0·3Estado de rollback en memoria = no durable

🔴 Bloqueante P0 Si el pod reinicia durante la ventana de 5 min, el patch queda aplicado y jamás se revierte.

Habéis puesto un esfuerzo enorme en durabilizar la cola (Redis Streams, PEL, dead-letter, reclaim)… y luego el rollback vive en un dict de proceso (IN_FLIGHT_ROLLBACKS, main.py:146) con asyncio.sleep(300). Rollout, OOM o spot-eviction en esos 5 minutos → se pierde el RollbackContext → la remediación queda sin evaluar y sin revertir.

Es la inconsistencia de resiliencia más grave del proyecto: máxima durabilidad en la ingesta, cero durabilidad en la acción correctiva.
Fix Persistir RollbackContext en Redis con TTL, y reevaluar los pendientes al arranque dentro de _periodic_reclaim / _periodic_cleanup. Reutiliza el patrón que ya tenéis en escalation_store.py.

§4Uso del LLM / IA

Bien Prompt estructurado con esquema JSON explícito, temperature=0 (reproducibilidad — decisión correcta y bien justificada), instrucción anti-alucinación, _clamp de confianza, saneado de risk. La salida cumple el checklist pedido (causa, confianza, explicación, acción, riesgo).

A mejorar

  • Sin contexto real (P0·1): el prompt anti-alucinación es un parche sobre un problema de arquitectura. No le pidas a un 1.5B "no inventes"; no le des la oportunidad inyectando el valor real.
  • No se fuerza salida estructurada de Ollama. Estáis parseando texto libre con 3 estrategias regex. Ollama soporta format: "json": 
    json={..., "format": "json",
      "options": {"temperature": 0, "num_predict": 512}}
    Elimina la mitad de los fallos de parseo y acota tokens.
  • Sin cap de tokens (num_predict) + http_timeout=360s → una divagación cuesta minutos.
  • Confianza no calibrada: autoevaluada por un 1.5B. Gatear una acción con ella es débil; con contexto real (P0·1) mejora, pero considera derivar la confianza de señales deterministas (nº de reinicios, coincidencia de runbook) además del self-report.

Vuestra comparativa "contexto > tamaño de modelo" es correcta y es justo el argumento para invertir en P0·1 antes que en un modelo mayor.

§5Autoremediación

Acciones auto-ejecutables: exactamente UNA → kubectl set resources (subir límite mem/cpu). Todo lo demás escala o se bloquea:

AcciónComportamiento
set resources (subir límite ≤2×)AUTO (con todos los gates)
rollout restartESCALATE (implica restart)
scaleESCALATE
delete podBLOCKED
cordon / drain / taintBLOCKED (bien)
Precisión de naming No es un "auto-remediador general": es un auto-escalador de límites de recursos con aprobación humana para todo lo demás. Nómbralo así en la memoria. La política de gates (decide_action, reglas 1→7.5) es la joya del proyecto.

Bugs / fragilidades concretas

  1. Selector hardcodeado app={name} (remediation.py:654). Si el deployment usa otra label → no_pods_found → healthy=False → rollback falso sobre una remediación que sí funcionó. Deriva el selector del .spec.selector.matchLabels real.
  2. check_pod_health mira solo containerStatuses[0] (:733). Pods multi-contenedor → evalúa el contenedor equivocado.
  3. El approve humano ejecuta comandos free-text del LLM, no el sintetizado. En main.py:972 se corre incident.safe_commands (texto del modelo), mientras el auto usa build_set_resources_command (determinista). Según vuestra nota F4 esos comandos suelen ser no ejecutables → el operador pulsa "Ejecutar" y no pasa nada. Unifica: el humano aprueba la acción estructurada.
  4. Rollback en memoria → ver P0·3.

§6Seguridad

Bien Sin shell=True (usa create_subprocess_exec + shlex, solo argv[0]=="kubectl") → sin inyección de shell. securityContext ejemplar (runAsNonRoot, readOnlyRootFilesystem, drop ALL). RBAC namespaced, sin recursos cluster-scoped. Secret de Mattermost por secretKeyRef.

Problemas

  1. Auth fail-open → P0·2.
  2. Mismatch de Secrets → P0·2.
  3. Envenenamiento del bucle RAG (prompt injection diferido). Los incidentes se persisten desde salidas del propio LLM (incluido raw_response) y se reinyectan como contexto en diagnósticos futuros. Un diagnóstico erróneo/malicioso persistido sesga decisiones posteriores. Mitigación: ingiere solo campos estructurados y sanitizados, no el crudo; marca procedencia.
  4. kubectl sin verificación de checksum (Dockerfile:16). ADD https://…/kubectl sin sha256 → riesgo de cadena de suministro. Añade sha256sum -c.
  5. ServiceAccount default con patch sobre deployments. Cualquier pod del namespace hereda el binding. Crea una SA dedicada aiops-agent y bindea contra ella.

§7Observabilidad — la mejor dimensión

Métricas Prometheus abundantes y bien etiquetadas (retries, extraction, diagnosis, remediation, rollback, chaos MTTD/MTTR, cola). Logs JSON estructurados. Historial de incidentes en ChromaDB. Pre-inicialización de counters para que aparezcan desde el arranque — detalle de profesional.

Falta Correlation-id de extremo a extremo. Se genera incident_id pero no se propaga como campo de log desde webhook → cola → diagnóstico → mattermost. Añadirlo en _handle_stream_entry y meterlo en el extra de cada log haría trivial rastrear un incidente. OpenTelemetry sería el siguiente paso (no hay trazas).

§8Escalabilidad y resiliencia

  • Techo de throughput duro: Ollama serializa la generación (~205-252 s/diagnóstico), consumidor in-process 1-a-1, replicas: 1 → ~1 alerta cada ~4 minutos. Una tormenta llena la cola y el MTTR se dispara.
  • Escalado horizontal bloqueado por el estado de rollback en memoria (P0·3). No puedes subir replicas sin corromper la evaluación de rollback.
  • Redis SPOF sin persistencia (redis.yaml: replicas:1, sin AOF/PVC). Si Redis reinicia: se pierden cola + dedup + escalaciones. Habilita AOF + PVC, o asúmelo como riesgo explícito.
  • Sin PDB para el agente ni para Redis (sí lo hay para Ollama).
Bien Fail-open de RAG/ChromaDB, fail-closed de la cola (503→Alertmanager reintenta), dedup, dead-letter, reclaim con min_idle > peor caso, self-heal de NOGROUP con backoff. La cola es ingeniería seria.

§9Calidad de código

Alta en general: tipado, docstrings con el porqué, dataclass/Enum, separación por módulos, 460 tests.

Deuda

  • main.py (1201 líneas) es un monolito. Mezcla 4 routers + orquestación del pipeline + formateo Mattermost + estado de rollback + métricas. Extraer: routers/, pipeline.py, rollback.py.
  • remediation.py (937 líneas) mezcla clasificación + parsing + executor + health + rollback.
  • Lógica de parseo duplicada entre is_structured_remediation y la regla 4.6 de decide_action. Extraer a helper.
  • Vestigios de la Fase 0 (Terraform): tf_generator.py, extraction.py, validation.py, endpoint /extract — código muerto en el binario de producción → amplía superficie y confunde el propósito. Sepáralo en paquete/imagen aparte o elimínalo.
  • Basura en repo: .DS_Store, .pytest_cache/. Limpiar con .gitignore + git rm --cached.

§10Integración con Mattermost

El mensaje incluye: recurso, namespace, severidad, diagnóstico, riesgo, confianza, comandos, explicación, fuentes RAG, acción ejecutada (dry-run vs escalación) y resultado de rollback. Cumple casi todo el checklist. Botones interactivos Aprobar/Rechazar con HMAC (cuando está configurado), TTL de escalación, y actualización del mensaje original al decidir. Bien resuelto.

§12Guion de brainstorm

Preguntas para pilotar la sesión de hoy, ordenadas para encajar con el roadmap activo (F3 slice C ya apunta al P0·1).

1 · ¿P0·1 y "slice C" son la misma microtarea?

La slice C que ya tienes planificada ("sellar target/valor desde labels + snapshot del cluster") es el fix del diagnóstico a ciegas, pero acotado a remediación. ¿Ampliamos su alcance para que el snapshot enriquezca también el prompt de diagnóstico (logs+events), o lo mantenemos mínimo (solo current_value) y dejamos el enriquecimiento de logs como F4?

2 · Fail-closed sin romper la demo

El fix de auth (P0·2) es barato pero cambia comportamiento. ¿Fail-closed solo cuando dry_run=false (prod real) y mantener fail-open en dev/test? ¿O metemos un flag explícito require_auth?

3 · ¿Durabilizar rollback ahora o asumir el riesgo para el chapter?

Para una demo de chapter con replicas:1 estable, el rollback en memoria "funciona". El coste es honestidad técnica en la presentación. ¿Lo arreglamos (reusa escalation_store.py) o lo documentamos como "known limitation" y priorizamos features visibles?

4 · Naming honesto en la memoria

¿Reetiquetamos el sistema como "auto-escalador de límites + aprobación humana" en la narrativa? Es más defendible ante un revisor que "auto-remediación" a secas, y el guardrail set es tu punto fuerte.

5 · Quick wins de cobertura de detección

3 reglas KSM (Pending/NotReady/FailedJob) son ~15 líneas de YAML y amplían la historia de "detecta N tipos de incidencia" sin tocar Python. ¿Entran en el deck?
Sugerencia de secuencia Si hoy solo cabe una microtarea de ~20 min: alinear secrets-setup.sh + fail-closed (P0·2) es la de mejor ratio impacto/esfuerzo y no depende del cluster. La grande (enrichment.py, P0·1) merece su propia sesión porque redefine el flujo de diagnóstico.
