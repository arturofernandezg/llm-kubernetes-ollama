## Decisiones tomadas y WHYs

### 1. Pin imagen a `:3fde9f8` (no `:latest`)
**Elegida:** `imagePullPolicy: IfNotPresent` + SHA explícito.
**Descartada:** Seguir con `:latest` + `imagePullPolicy: Always`.
**WHY:** Con `:latest`, `kubectl rollout undo` no tiene a qué volver — cualquier `rollout undo` simplemente re-despliega el mismo `:latest`. Pinear el SHA hace el rollback determinista. Además, `imagePullPolicy: Always` fuerza un pull en cada restart de pod, añadiendo latencia de red. `IfNotPresent` usa la imagen en caché del nodo.

### 2. smoke.sh como script bash (no comandos manuales)
**Elegida:** `scripts/smoke.sh` ejecutable, mismo patrón que `chaos.sh`.
**Descartada:** Secuencia curl documentada solo en session doc.
**WHY:** La reproducibilidad es el objetivo de esta sesión. Un script versionado en el repo puede ejecutarse en cualquier despliegue futuro, en CI, o como gate pre-merge. Los comandos manuales se pierden cuando el repo cambia de manos.

### 3. Backup ChromaDB: procedimiento manual (no CronJob)
**Elegida:** Procedimiento `kubectl exec + tar + kubectl cp` documentado en `docs/03-kubernetes.md`.
**Descartada:** CronJob K8s con script de backup automático.
**WHY:** Un CronJob requiere montar un segundo PVC o configurar subida a GCS — scope excesivo para el TFG. El backup manual es suficiente para proteger los 16 runbooks y el histórico de incidentes durante la defensa.

### 4. Sesión de pruebas separada
**Elegida:** Marcar Mini-Fase 4 como "en curso" y planificar sesión de pruebas E2E independiente.
**WHY:** Las 6 sesiones del plan entregaron código y artefactos, pero ninguno ha sido ejecutado en cluster en este bloque. Una sesión dedicada solo a pruebas permite iterar sobre fallos sin mezclar desarrollo con verificación.

## Secuencia de ejecución (para la sesión de pruebas)

### Gate 0 — pytest (BLOQUEANTE)
```
pytest agent/tests/ -v --tb=short
```
Esperar ~310 tests en verde. Si falla: corregir antes de continuar.

### Gate 1 — Cloud Build
```
gcloud builds submit --config cloudbuild.yaml --substitutions=COMMIT_SHA=$(git rev-parse --short HEAD)
```
Anotar el SHA producido (debe ser `3fde9f8` si no hay commits nuevos).

### Gate 2 — Deploy + rollout
```
kubectl apply -f k8s/deployment-agent.yaml -n arturo-llm-test && kubectl rollout status deployment/agent -n arturo-llm-test --timeout=180s
```

### Gate 3 — Verificar logs limpios
```
kubectl logs -n arturo-llm-test deploy/agent --tail=30
```
Buscar startup OK. Si aparece `WARNING: WEBHOOK_SECRET not set` es esperado (optional). Verificar que `REMEDIATION_ROLLBACK_ENABLED=true` aparece en log de config.

### Gate 4 — Smoke test
```
bash scripts/smoke.sh
```
Debe terminar `=== SMOKE TEST PASSED ===` con exit 0.

### Gate 5 — Métricas rollback presentes
```
kubectl exec -n arturo-llm-test deploy/agent -- curl -s localhost:8000/metrics | grep aiops_remediation_rollback_total
```

### Gate 6 — Chaos experiments (uno a uno, NO en paralelo)
```
bash scripts/chaos.sh oom
bash scripts/chaos.sh crashloop
bash scripts/chaos.sh bad-image
bash scripts/chaos.sh cpu
bash scripts/chaos.sh cleanup
```
Para cada experimento: anotar `T_pod_fail`, esperar alerta en logs del agente (`kubectl logs -n arturo-llm-test deploy/agent --since=15m | grep -i 'alert\|chaos'`), anotar MTTD real. MTTR = desde `startsAt` hasta mensaje Mattermost recibido.

### Gate 7 — Capturar MTTD/MTTR
Rellenar tabla en `docs/12-chaos-engineering.md` líneas 103-106 con los valores reales:
```
| 2026-05-XX | OOMKilled | 0m | <T_pod_fail> | <MTTD_s> | <MTTR_s> | <confidence> | <outcome> | |
```

### Gate 8 — Screenshot Grafana
```
kubectl port-forward svc/grafana-svc 3000:3000 -n arturo-monitoring
```
Abrir `http://localhost:3000/d/aiops-chaos` → capturar screenshot → guardar como `docs/img/grafana-chaos.png`.
