El LLM queda reducido a *field + dirección*. Métrica `aiops_enrichment_total{gathered|workload_unresolved|skipped|error}`. **F-17 (2026-07-10)**: el snapshot gana `logs_tail` (`kubectl logs --tail`, `--previous` si el contenedor murió/reinició — ahí está la traza del OOM — con fallback a current) + `recent_events` (field-selector por pod, newest-last), ambos fail-soft con caps duros (líneas/chars/nº eventos, config `enrichment_log_*`/`enrichment_events_limit`); `format_cluster_facts` los renderiza en bloques separados **RECENT LOGS / RECENT EVENTS** (el texto libre observado no se mezcla con los hechos estructurados autoritativos). Es el 1er uso genuinamente *nuevo* del LLM: razona sobre lenguaje libre, cero ejecución.
- **Pipeline RAG+LLM**: 16 runbooks en ChromaDB; triple fail-open (ChromaDB / Ollama / ambos). **ChromaDB no bloqueante (F-03)**: todas las llamadas HTTP síncronas de ChromaDB (`retrieve_context`, `ingest_runbook`/`ingest_incident`, `ensure_collections`, query del slash) van envueltas en `asyncio.to_thread` — no congelan el event loop. **Retrieval guiado por metadata (R1)**: el runbook query se filtra por `error_class` derivado del alertname (`alertname→error_class` determinista, resuelve el prefijo `KubePod` de Prometheus), con fallback semántico si el filtro no matchea. Medido en cluster: **p@1 73.3%→100%, p@3 86.7%→100%** (N=15). "Determinista donde se puede, semántico como fallback".
- **Motor de remediación**: 9 reglas en cascada + **re-sourcing de decisiones** ("el modelo propone, el motor dispone"). Dimensión **CPU además de memoria** (`resources.limits.cpu`, field-agnostic vía `_LIMIT_FIELD_PARSERS` y `_limit_resource`; capture/revert derivan el recurso de `field`). `is_structured_remediation()` es la **fuente única** de elegibilidad (field elegible + name/ns/container + valores parseables + solo-subir + namespace en el allow-list `arturo-`); cuando dispara, el motor **sintetiza** el comando con `build_set_resources_command` (determinista, acotado ≤2× por la regla 4.6, reversible por snapshot) y **bypasea la regla 5** (el `risk` auto-rating del modelo lo sustituye el bound del motor; el suelo de confianza de la regla 6 se mantiene). Auto-CPU tras flag `remediation_auto_cpu_enabled` (default off, escalate-first hasta validar). Clasificación regex BLOCKED > SAFE > MUTATING. **Cooldown por workload (F-01, working tree)**: SETNX `aiops:cooldown:{ns}/{name}` TTL 600s (> ventana rollback) en la rama auto estructurada — un solo patch auto por workload por ventana (corta el patch-storm de alertas re-firing); bloqueado o Redis no verificable → ESCALATE fail-closed con el comando determinista para el humano.
- **ChatOps**: Mattermost + botones HMAC-SHA256; escalaciones persistidas en **Redis** (`escalation_store.py`, fail-open); slash command `/aiops`. **Auth fail-closed (v2 P0·2)**: con `REMEDIATION_DRY_RUN=false` un `WEBHOOK_SECRET`/`MM_COMMAND_TOKEN` vacío rechaza (401) en vez de fail-open — no hay remediación no autenticada; `secrets-setup.sh` alineado con las claves que el deployment lee de verdad + **guard anti-placeholder** (aborta si detecta `<...>` sin sustituir — respuesta al incidente que pisó el webhook real). **Paridad humano/auto (`cb2d1db` + `ca159be`)**: `process_remediation` sintetiza el `structured_command` UNA vez; la escalación estructurada guarda/enseña ese comando (no el free-text del LLM) y el approve captura snapshot + programa rollback igual que el auto, reusando el `incident_id` — *what you approve is what runs*. **Cierre del gap R2-humano (`ca159be`)**: el `PendingEscalation` lleva ahora `incident_doc_id` (round-trip por Redis) → la rama approve pasa `doc_id`+`remediation` a `_schedule_rollback_evaluation` (espejo exacto del auto), así el veredicto `cured`/`rolled_back` de un fix **aprobado por un humano** también alimenta el bucle de aprendizaje R2 (`aiops_feedback_verdict_total` + doc en ChromaDB re-marcado) reusando el mismo `doc_id`. Mensajes muestran la confidence grounded ("100% grounded del cluster; el modelo dijo 65%"). **F-04**: timeout dedicado `mattermost_timeout=10s` (antes heredaba los 300s del LLM → retries de minutos con MM caído). **C-07 (2026-07-10, factibilidad ≠ seguridad)**: pre-flight `kubectl auth can-i` de los comandos free-text al escalar (`auth_can_i_args`/`check_command_executable`/`partition_by_permission`, fail-open salvo "no" explícito) — los denegados por RBAC se muestran como "comando sugerido (sin permisos)" en vez de ejecutar-y-fallar; el comando estructurado del motor NO pasa por el check (determinista, conocido-ejecutable); NO se amplió RBAC. **C-08 (2026-07-10, doble botón model/×2)**: cuando el LLM propone >2× (el caso 16× del chaos), la escalación ofrece **dos botones bien formados** — `approve_engine` (×2 determinista, recomendada, ✅) y `approve_model` (valor del LLM, ⚠️) — vía `structured_command_variants` (ambos sintetizados con `build_set_resources_command`, nunca free-text); **cada botón firma su propia acción por HMAC** (la elección model↔engine no es flippable en tránsito); 1 botón (acción legacy `approve`) si coinciden o el current no es doblable; el safety-net (snapshot/rollback/cooldown) es value-agnostic y no cambia. Convierte la decisión oculta del motor en una elección explícita y auditada del operador.
- **Bucle observacional (R5, 2026-07-10)**: las alertas `resolved` de Alertmanager cierran el bucle para TODAS las clases (no solo memoria) — `_alert_fingerprint` (fuente única con el dedup) correla el `resolved` con el incidente activo vía `agent/incident_index.py` (Redis `incident:active:{fp}`, TTL 3600s, fail-open, pop = GET+DEL). En un hit: métrica `aiops_incident_resolution_seconds{error_class}` (MTTR observado) + `aiops_incident_resolution_total{correlated}`; y si el incidente NO esperaba veredicto de rollback (`awaits_verdict=False`: escalados/suggest-only), re-upserta el doc ChromaDB a `resolved_observed`. **Jerarquía de señales**: el veredicto del motor (`cured`/`rolled_back`, verificado) es fuerte y dueño del outcome; `resolved_observed` (observado, causa sin verificar) es débil y nunca lo pisa — el approve suelta la entrada del índice al programar rollback (cierra esa race). Tapa el borde honesto "safety ≠ correctness" para no-memoria con un outcome real y barato. **Validado en cluster 2026-07-13 (S7): primer valor real, `aiops_incident_resolution_seconds{OOMKilled}` = 92.47s** (esa serie ya no existe — Prometheus stateless, se evaporó con el churn del 07-14, F-27). **Matiz honesto (validado en vivo 07-15): el flujo con aprobación humana NO regenera esta serie** — al aprobar en Mattermost el índice hace `pop` (para que el veredicto del rollback, más fuerte, sea dueño del outcome), así el `resolved` posterior da `correlated="miss"` y no emite `_seconds`. R5 solo produce muestra en un "hit" (un `resolved` que correla con un incidente aún indexado: escalados no aprobados). → **En el flujo humano la evidencia fuerte del Gate 8 es `aiops_feedback_verdict_total{outcome="cured"}`, no R5.**
- **Rollback durable (v2 P0·3)**: el `RollbackContext` se persiste en Redis (`rollback_store.py`, espejo de `escalation_store`) además del dict en memoria; `_recover_rollbacks()` re-arma al arranque los rollbacks que quedaron a mitad de ventana tras un reinicio del pod (antes: el patch quedaba aplicado y **nunca** se revertía). `_evaluate_rollback` duerme el tiempo restante hasta el deadline, no el timeout fijo.

## Modos de fallo conocidos

| Componente | Fallo | Mitigación |
|---|---|---|
| Alert parsing | Labels inesperados/vacíos | Defaults seguros, log del payload raw |
| Embeddings | Error sin vecinos en ChromaDB | Threshold mínimo; sin match → LLM zero-shot |
| Retrieval | Docs irrelevantes | Filtrado por metadata, top-K conservador (3-5) |
| LLM | Hallucination / comandos incorrectos | Structured output + validation layer + whitelist; sin JSON → fallback |
| LLM | Comandos destructivos | Blacklist explícita; nunca auto-ejecutar sin validation layer |
| Auto-remediación | **Target/valor de la remediación alucinados** por el modelo pequeño: el comando se sellaba con `name/namespace/container/current/new` de `proposed_action` (LLM) y el 1.5b los inventa → `NotFound`/`unparseable` | ✅ **Resuelto (v2 Eje A, `cb2d1db`)**: enrichment sella identidad (ownerReferences + gate de existencia), `current_value` y selector desde el snapshot; temp=0 mata la varianza de valor; síntesis `2×current` si el valor LLM es inusable; target sin confirmar o kind≠Deployment (F-02) → regla 4.7 escala. El LLM queda en *field + dirección*. Pendiente re-validar chaos en cluster |
| Auto-remediación | **Patch-storm**: la alerta re-firing dentro de la ventana de rollout/rollback dispara un segundo 2× encima del primero | ✅ **Resuelto (F-01, working tree)**: cooldown por workload (SETNX TTL 600s) — un patch auto por workload por ventana; bloqueado/Redis dudoso → ESCALATE fail-closed con el comando determinista |
| Rollback | **Rollback falso**: health-check post-patch con selector adivinado `app={name}` → 0 pods → "no sanos" → revertía una remediación que funcionó | ✅ **Resuelto (v2 Eje A)**: selector derivado de `match_labels` del `.spec.selector` real (fallback `app={name}` solo sin enrichment) |
| Operación | **Scripts-plantilla con placeholders**: `secrets-setup.sh` ejecutado sin editar pisó el secret real del webhook | ✅ **Resuelto (working tree)**: guard `abort_if_placeholder` — cualquier `<...>` sin sustituir aborta ANTES de tocar kubectl. Recuperación documentada: `printenv` del pod vivo pre-reinicio + token en MM UI |
| Auto-patch | Fix aplicado pero alerta no cesa | Rollback automático (monitoriza salud del pod, revierte + escala) |
| Rollback | **Pod reinicia dentro de la ventana de espera** (rollout/OOM/spot) → dict en memoria + tarea `sleep` perdidos → patch aplicado que nunca se revierte | ✅ **Resuelto (v2 P0·3)**: `RollbackContext` persistido en Redis (`rollback_store.py`); `_recover_rollbacks()` re-arma al arranque y evalúa el tiempo restante. Coherente con la cola durable de F2 |
| Rollback | **Falso rollback por restart benigno**: el health-check post-patch cuenta restarts **sin mirar el motivo** → un workload que reinicia por exit limpio (no por crash) se lee como "no sano" → revierte un fix que funcionaba. Observado en cluster 2026-07-04 con el manifiesto chaos (`stress --timeout 60` sale exit 0 cada 60s tras subir la memoria) | ✅ **Resuelto (C-01, 2026-07-09)**: `check_pod_health` trae `lastState.terminated.reason` como 3er campo del jsonpath; un restart solo marca unhealthy si el motivo ∈ `_FAILURE_REASONS` (OOMKilled, Error…) — los benignos (`Completed`, vacío) se loguean y se ignoran. Decisión: solo la **evidencia positiva de fallo** dispara rollback (unknown→unhealthy reintroduciría el falso-rollback; el coste de un rollback perdido es leve frente a revertir un fix que curaba). Mitigación previa (chaos sin `--timeout`) confirmada en el run del 07-06 |
| Chaos/operación | **Horno nocturno**: un target "curado" con `stress` infinito **ya no OOMea pero quema CPU para siempre** (propiedad no anticipada del fix "sin `--timeout`"). El target del 07-04 quedó vivo a 512Mi ~36h → HighCPU flapping toda la noche, ~30 diagnósticos LLM molidos, docs basura en ChromaDB, escalaciones apiladas | ✅ **Lección → gate**: el teardown (`delete deployment` + limpieza `rollback:*`/`escalation:*`/cooldown en Redis) es el **último gate del run**, no una tarea posterior que dependa de la memoria humana — codificado en `scripts/chaos_arc.sh` (`trap EXIT`) y en la skill `/chaos-run`. Mejora propuesta del manifiesto (a validar): `stress --vm-hang 0` (asigna, retiene y duerme → OOMea a 32Mi pero el cured a 512Mi queda silencioso, CPU~0) |
