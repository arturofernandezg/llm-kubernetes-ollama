El problema que resuelve

🚨 El operador de guardia

Son las 3am. Prometheus dispara. El operador recibe la página, abre el runbook correcto (si lo encuentra), diagnostica manualmente, aplica el fix.

  • MTTR de minutos a horas
  • Carga cognitiva alta bajo presión
  • Un fallo humano = incidencia mayor

📄 Runbooks dispersos

16+ runbooks en wikis, repos y docs. Ninguno está en el flujo de alerta. El operador los busca bajo estrés, sin contexto del pod/namespace afectado.

  • Conocimiento desconectado del sistema de alertas
  • Sin histórico de incidentes anteriores
  • Sin priorización por severidad

🔒 Restricciones telco

Entorno MasOrange: los datos del cluster no pueden salir a APIs externas. Sin Cloud NAT. Sin presupuesto por token de LLM.

  • OpenAI / Vertex AI descartados
  • El LLM tiene que correr in-cluster
  • Sin GPU garantizada en GKE spot
Este slide es el "por qué". Las tres restricciones juntas son las que hacen interesante el problema: no es solo "voy a usar un LLM" — es "tengo que hacerlo con un modelo pequeño, en CPU, sin salir del cluster, y que sea seguro para producción". Tiempo estimado: 2 minutos. Puedes leer las tarjetas de izquierda a derecha y añadir: "El proyecto nace de intentar resolver estas tres tensiones a la vez."

La pregunta de investigación

"¿Puede un modelo de lenguaje de 1.5B parámetros, corriendo en CPU sin GPU y sin APIs externas, asistir la remediación de incidencias en Kubernetes de forma segura?"

Hipótesis

Sí — si se combina con tres capas de control independientes:

  • RAG in-cluster para contexto relevante (runbooks + histórico)
  • Validation layer (9 reglas) que bloquea acciones destructivas antes de ejecutar
  • Human-in-the-loop cuando la confianza o el riesgo lo requieren

Validación

  • Evaluación offline: N=10 alertas, RAG vs zero-shot
  • Safety 100% SAFE con RAG (vs 25% zero-shot)
  • Confidence +37% relativo con contexto RAG
  • E2E verificado en GKE: alerta → diagnóstico → Mattermost → operador
  • Chaos engineering: 4 experimentos en cluster real
Este slide establece el marco científico. El tutor quiere ver que hay una hipótesis formulada y un método de validación — no solo "construí cosas". Recuerda: NO afirmar MTTD/MTTR como medidos. Los números de safety y confidence SÍ son reales (docs/10-evaluation.md, N=10, metodología offline). Tiempo estimado: 2 minutos. Arquitectura del sistema

Todo in-cluster — los datos no salen del GKE

Prometheus (métricas + 6 reglas) │ alerta firing ▼ Alertmanager (routing) │ POST /webhook/alert ▼ FastAPI Agent ◄──► ChromaDB │ (16 runbooks + histórico) │◄──────────────┘ contexto RAG │ ▼ Ollama (qwen2.5:1.5b, in-cluster) │ JSON: diagnosis + commands │ + confidence + risk ▼ Validation Layer (9 reglas) │ ├─ risk=low, conf≥0.8 ──► kubectl patch │ │ │ rollback si falla │ └─ risk=high / conf<0.8 ──► Mattermost │ ✅ Aprobar / ❌ Rechazar │ K8s API + ChromaDB (feedback loop)

Propiedades de diseño clave

  • Fail-open everywhere — si ChromaDB o el LLM fallan, el pipeline degrada (diagnóstico sin contexto) pero nunca bloquea la alerta
  • Validation-first — el LLM nunca ejecuta directamente; dos capas independientes: whitelist regex + motor de decisión
  • Soberanía de datos — LLM, vector store y ChatOps corren en el cluster GKE; ningún dato sale
  • Feedback loop — cada incidente (outcome + fix) se ingesta en ChromaDB; el RAG mejora con el tiempo

Stack (todo in-cluster)

Python 3.11 · FastAPI Pydantic v2 · httpx Ollama qwen2.5:1.5b nomic-embed-text 768d ChromaDB 0.6.3 Prometheus · Alertmanager Grafana · Mattermost GKE e2-standard-2 spot Cloud Build · Artifact Registry
Este slide es la arquitectura completa. Deja que el tutor la absorba. Puntos a destacar en voz: 1. "Todo el flujo es asíncrono — Prometheus dispara, el agente procesa, Mattermost notifica. No bloquea nada." 2. "La validation layer es independiente del LLM — aunque el LLM se equivoque, las reglas capturan el error." 3. "Fail-open: si ChromaDB cae, el agente sigue funcionando con diagnóstico sin contexto RAG. Una alerta perdida sería peor." 4. "El feedback loop es lo que diferencia esto de un sistema estático: cada incidente alimenta el vector store." Tiempo estimado: 3 minutos. Es la slide más densa — no te apresures.
